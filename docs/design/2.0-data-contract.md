# Rapportkit 2.0: data contract (draft)

Status: sketch for discussion. Nothing here is implemented. Written against what 1.4.1 actually produces.

## Goal

Split the kit in two parts that only meet in a folder of files:

- **Collector** (`Run-Rapportkit.ps1`): reads Azure and the tools, writes a *run package*. Runs on the customer's machine.
- **Report engine**: reads one or more run packages of the same tenant, builds the report and the comparison (deltas, trends). It never talks to Azure.

Decisions (2026-11-03):

- **PowerShell for both parts.** Portability first: the engine runs on the consultant's own Windows machine with nothing to install, and reuses the existing report code (`lib/Report.ps1`, `lib/StructurePage.ps1`, language packs, branding). The contract is plain JSON Lines, so a port to another language stays possible.
- **Consultant-run, not hosted.** The customer runs the collector and sends the package; the consultant keeps the history and builds the delta reports on their own machine, for example for a monthly review. No customer data on shared servers. No server or App Service packaging.
- **The output is a folder of static HTML**, so a finished delta report can be handed to the customer as files, without a server on either side.

The contract is the run package. Everything below is about making it small, stable and comparable.

## Run package

```
<tenant>/<runId>/
  manifest.json          what this run is, and how far it got
  data/                  normalised, what the engine reads
    scopes.jsonl         management groups and subscriptions
    networks.jsonl       virtual networks
    peerings.jsonl
    resources.jsonl
    findings.jsonl       one row per finding, all sources
    rules.jsonl          one row per rule (explanation, remediation, link)
    assignments.jsonl    role and policy assignments
    defender-plans.jsonl
    metrics.jsonl        numeric time-series points
  raw/                   the tools' own output, untouched (optional, not needed by the engine)
```

- JSON Lines, UTF-8 without BOM, one object per line. Easy to stream, diff and read from any language. No CSV: AzGovViz uses `;`, the rest `,`, and the Swedish column names stay behind.
- All field names English, camelCase. The engine needs only `manifest.json` and `data/`. In the real run `raw/` is hundreds of MB (`PolicyAll.json` 43 MB, `DefinitionInsights.html` 47 MB); `data/` should be a few MB. This is also what gets uploaded to a server, and it carries less than `raw/`.
- IDs: Azure resource IDs are case-insensitive, so every `*Id` is stored lower-cased.

## manifest.json

```json
{
  "schema": "rapportkit.run/1",
  "runId": "9d0c…",
  "tenantId": "a6017aee-…",
  "startedAt": "2026-10-30T13:18:00Z",
  "finishedAt": "2026-10-30T13:52:00Z",
  "period": "2026-10",
  "collector": { "name": "azure-rapportkit", "version": "2.0.0" },
  "tools": { "azqr": "4.3.0", "governanceVisualizer": "6.7.2", "maester": "2.3.0" },
  "coverage": { "subscriptionsVisible": 12, "subscriptionsCollected": 12, "capped": false },
  "sources": {
    "azqr":       { "state": "OK",      "rows": 214 },
    "maester":    { "state": "OK",      "rows": 753 },
    "azgovviz":   { "state": "OK",      "rows": 3120 },
    "defender":   { "state": "Partial", "rows": 88, "note": "recommendations: Internal Server Error (sub 3)" },
    "cost":       { "state": "OK",      "rows": 144 },
    "structure":  { "state": "OK",      "rows": 31 }
  },
  "files": { "data/findings.jsonl": { "rows": 1055, "sha256": "…" } },
  "anonymized": false
}
```

Why each part exists:

- `schema` lets the engine refuse or migrate a package it does not understand.
- `sources.*.state` decides whether a source is comparable (see rules below). The Defender API really does fail transiently; that must never read as "all findings fixed".
- `coverage` exists because the collector today stops at `-MaxPortalSubscriptions` (25) silently apart from a warning. A cap that differs between two runs would look like subscriptions appearing and disappearing.
- `files.sha256` detects a damaged or hand-edited package after transfer.

Implemented so far (unreleased): `lib/Package.ps1` and `Export-RunPackage.ps1` turn a 1.x result folder into `manifest.json` + `data/` (findings, rules, resources, scopes, networks, peerings, metrics, defender-plans). Not yet written: role and policy assignments. The collector does not write the package itself yet.

## Row shapes

### findings (the core of the comparison)

```json
{ "key": "azqr:app-009:/subscriptions/…/sites/garminbodycomp",
  "source": "azqr", "ruleId": "app-009", "status": "open",
  "severity": "medium", "category": "security",
  "title": "App Service should use VNET integration",
  "subscriptionId": "63621c47-…", "resourceId": "/subscriptions/…", "resourceType": "microsoft.web/sites",
  "detail": "VNET integration not configured" }
```

- `key` = `source:ruleId:resourceId` (resource id empty for tenant-wide tests). This is the identity across runs.
- `status`: `open`, `passed`, `skipped`, `error`. Only `open` counts as a finding in the report; `passed` is kept so a fix can be told from a rule that stopped running.
- `severity`: `critical|high|medium|low|info`, mapped per source.

| Source | ruleId | resourceId | Notes from the real data |
|---|---|---|---|
| azqr | `Recommendation Id` | `Resource Id` | stable; see open question on masking |
| Maester | `Tests[].Id` (`CIS.M365.1.1.1`) | none | 2–10 of 753 tests changed result between four runs a few hours apart, mostly `skipped`↔`failed` |
| Defender | assessment `name` (`Nyckel`, added in 1.4.1) | `resourceDetails.Id` | status `Unhealthy`/`Healthy`/`NotApplicable` mapped to open/passed/skipped |
| AzGovViz clean-up | `Intent` | `Resource` | optional, low priority |

### rules (answers "do we still need the tools' own reports?")

```json
{ "source": "azqr", "ruleId": "app-009", "title": "…", "description": "…",
  "remediation": "…", "learnUrl": "https://learn.microsoft.com/…", "defaultSeverity": "medium" }
```

One row per rule, not per finding, so the long texts are stored once. Sources: azqr `recommendations.csv` (guidance + link), Maester `Tests[]` (title, severity, tags, the explanation in `ResultDetail`, trimmed), Defender assessment metadata. With this the finding drill-down page needs no link to a tool report. Links to the raw tool reports stay as a fallback.

### scopes, networks, peerings, resources, assignments, defender-plans

Plain projections of what is already collected (AzGovViz `SubscriptionDetails`/`RoleAssignments`/`PolicyAssignments`, `struktur\*.csv`, azqr inventory), with `…Id` keys and Swedish values replaced (`Typ` becomes `type: managementGroup|subscription`). `scopes` carries `parentId` and `path`, so a moved subscription is a change of `parentId`, not a delete plus an add.

### metrics (the graphs)

```json
{ "name": "secureScore.percent", "scopeId": "63621c47-…", "value": 28.6, "unit": "percent" }
```

The point's time is the run's `finishedAt`, not stored per row. Planned names:

| Name | Scope | From |
|---|---|---|
| `secureScore.percent`, `secureScore.points` | subscription | Defender |
| `findings.open.<source>.<severity>` | tenant | derived from findings |
| `maester.passed/failed/skipped` | tenant | Maester |
| `resources.count` | subscription | inventory |
| `cost.month` (with `period` and `currency` as extra fields) | subscription | cost |

Cost is special: each run holds 12 months, so the engine merges runs by month and the newest run wins. All other metrics are one point per run.

## Comparison rules

Between run A (older) and run B (newer) of the same tenant:

1. A source is compared only if `state` is `OK` in both. `Partial`, `Failed` and `Skipped` produce "not comparable", never "resolved".
2. Within a comparable source, per `key`: only in B = **new**, only in A = **resolved**, in both with different severity = **changed**. A finding whose resource is gone from `resources` in B is **resolved (resource removed)**, shown apart from a real fix.
3. For Maester, `skipped` ↔ anything is reported as "test coverage changed", not as a regression or an improvement; `passed` ↔ `failed` is a real change.
4. Compare subscriptions by `subscriptionId` only, never by name.
5. Charts need at least two comparable points; with one run the page shows the current value only.

## Migration of existing runs

An importer turns a 1.x run folder into a 2.0 package (`manifest.json` + `data/`, `raw/` left in place):

- 1.4.1 runs: direct mapping, keys exist.
- 1.4.0 and older: no `PrenumerationId` in the Defender/cost files; map name to id through AzGovViz `SubscriptionDetails` or azqr inventory. No `Nyckel` in recommendations; fall back to key `defender:<displayName>:<resourceId>`, flagged in the manifest as `keyQuality: "derived"` so a later rename shows as new + resolved rather than silently wrong.
- `run-summary.json` supplies version, times and tool versions; `sources.*.state` comes from its step statuses.

The real tenant run in `rl\2026-10` is the first test case; the beta customer's 1.3 run is the second.

## Anonymisation across runs

Today aliases are numbered per run (`Subscription 1`, in discovery order), so the same subscription can get a different alias next month. For comparisons the alias must derive from the value: for example `HMAC(secret, value)` shortened, with the secret kept per customer in the history folder and never in the package. Lower priority now that the history stays with the consultant: it matters only for anonymised demo reports built from several runs.

## Prototype results

A throw-away converter (not in the repo) built `findings` and `rules` from the real tenant run in `rl\2026-10` (azqr, plus four Maester runs from the same day) and applied the comparison rules. Defender and cost could not be tested: the `portal\` folder of that run is empty (the run used `-ReportOnly` with tools skipped), and no 1.4.1 run exists yet.

| Test | Result |
|---|---|
| azqr key `rule:resource` unique | 37 findings, 37 unique keys, 0 duplicates. All 37 are in one subscription, so a masking collision between subscriptions could not occur here and is untested. |
| Every finding has a rule | Yes: 314 azqr rules, 0 findings without one. |
| Maester key stable | 753 tests, 753 unique ids, identical id set in all four runs. |
| Maester noise | Between runs of the same tenant 1 test went `passed`→`failed` (a real new finding) and 1–8 went `skipped`↔`failed`/`passed`. With rule 3 these show as "coverage changed", so the real change stands out. Without rule 3 the same data would show up to 9 phantom changes per comparison. |
| Twin run (a run against itself) | 790 rows, 0 new, 0 resolved, 0 changed. |
| Synthetic pairs | New, resolved, changed severity, resolved because the resource was removed, coverage change and `Partial`/`Failed` source all give the expected result (7 cases). |
| Size | `findings.jsonl` 0.19 MB (790 rows), `rules.jsonl` 0.27 MB without Maester explanations. `raw/` is 208 MB (AzGovViz 158, Maester 46 for four runs, azqr 0.5). Other `data/` files are not measured yet. |

### Live run with 1.4.1 (Defender, cost, structure)

A read-only run of the 1.4.1 collector against the real tenant (tools skipped, `-NoEncrypt`, one visible subscription) gave:

| Test | Result |
|---|---|
| New columns present | `PrenumerationId` in all five Defender/cost files, `Nyckel` in recommendations, `KontrollId` in controls. Both keys are GUID-like and unique. |
| Keys unique, twin run | 2 recommendation keys, 0 duplicates; twin comparison gives 0 changes. |
| Number format | **The CSVs use the machine's culture**: `"0,2857"`, `"236,38"` (decimal comma on this Swedish machine). A machine with another culture writes `0.2857`. The importer must accept both; `data/` uses invariant JSON numbers. A parser that handles `0,2857`, `0.2857`, `1 234,56`, `1.234,56` and `1,234.56` passed. |
| Defender list vs controls | The recommendation list held 2 rows, both `Healthy`, while the Secure Score controls report 1 unhealthy resource (`Enable MFA`). The kit already warns about this. For the contract: when controls show more unhealthy resources than the list, `sources.defender.state` is `Partial`, and per-control metrics (`secureScore.control.unhealthy`, keyed by `KontrollId`) are the comparable series, not the recommendation list. |
| Cost | 13 monthly rows (2025-11 to 2026-11). The last one is the current, incomplete month (26.12 after three days). Mark it `partial` so a chart does not show a drop; the next run replaces it. |
| Structure | Management group and VNet ids from the old 1.4.0 run and the live run are identical (8 and 5). |

Migration, simulated by stripping the id columns from the live files (as a 1.4.0 collector would have written them) and mapping subscription name to id through AzGovViz `SubscriptionDetails` from the older run:

| Test | Result |
|---|---|
| Subscription ids | Mapped to the same ids as the exact files. |
| Metrics (score, cost, plans) | All 18 keep scope and name; 0 values differ. |
| Controls | Without `KontrollId` they are keyed by name (`name-enable-mfa`), so they do not match the id-keyed new rows (6 keys differ). The engine can bridge them through the display name, which both files carry. |
| Defender recommendations | Derived keys (title + resource) never equal the assessment-id keys, so a comparison across the 1.4.0 → 1.4.1 boundary would show every Defender finding as resolved plus new. |

What this changed in the design:

- **Cross the key boundary by title.** When either side has `keyQuality: "derived"`, match Defender findings on `title` + `resourceId` instead of `key`, or leave them out of the delta and compare only the metrics. The first is better; both avoid the mass "resolved + new".
- **Source states are finer than the steps.** Done in 1.4.2: `run-summary.json` has a `sources` section with `azgovviz`, `azqr`, `maester`, `structure`, `plans`, `secureScore`, `secureScoreControls`, `recommendations` and `cost`, each with `state` and `note`. `recommendations` is `Partial` when the controls report more unhealthy resources than the list holds (checked on the real tenant).
- **Culture.** Optional collector change later: write numbers with the invariant culture in the CSVs. Not needed if the importer reads both.

What this changed in the design:

- **Maester `ResultDetail` is two things.** `TestDescription` (about 1.0 MB per run) is generic rule text; `TestResult` (78 KB) and `SkippedReason` (47 KB) are specific to the tenant. The generic part goes in `rules`, the rest in `findings.detail`. Since the rule text is identical from run to run, the engine keeps the newest version per `source`+`ruleId` instead of one copy per run.
- **Statuses.** Maester also returns `Error` (1 test, in all four runs) and `NotRun`; they map to `error` and `skipped`. 47 tests have an empty or missing severity and map to `info`.
- **Severity names** differ in case per tool (`High`, `Medium`, `Info`); the converter lower-cases them.

## Open questions

1. ~~azqr masks subscription IDs by default.~~ Fixed in 1.4.2: the kit passes `--mask=false` (checked on azqr 4.3.0 against the real tenant: real ids in `Subscription Id` and `Resource Id`).
2. ~~Engine language.~~ Decided: PowerShell (see Goal).
3. **Where the history lives and how it is protected.** Provisional (2026-11-03): packages are transferred encrypted (`.rkenc`, already solved), then kept readable on the consultant's disk-encrypted machine, under an NDA with the customer. A customer who receives the engine has bought a service that includes it. Retention and deletion at the end of an assignment still need a written rule; revisit before the first long-running customer, and consider keeping packages encrypted at rest if a customer's terms ask for it.
4. **Maester explanation text.** About 1 MB of generic rule text per run, kept once per rule (see prototype results). Decide whether to store it all or trim to the first paragraph plus the link.
5. ~~Who uploads.~~ Decided: the customer sends the package as today (e-mail or the agreed channel); the consultant imports it.
6. **Package privacy.** `data/` still holds resource names, IDs and role assignments. It needs the same `.rkenc` treatment as today's zip when it leaves the machine.
